# 开发日志与关键决策记录

> 用途：记录本项目开发过程中的难点、踩坑、决策与迭代过程。
> 面试时这是"我如何思考问题"的证据，比最终代码更重要。

## 一、项目信息

- 项目：客服工单处理 Agent（求职作品集，按公司标准开发）
- 技术栈：Python 3.10+ / LangGraph / LangChain (langchain-openai) / FastAPI / SQLite / DeepSeek API
- 开发工具：VS Code + Claude Code（Claude Code 写代码，架构与验收由羔丸把关）

## 〇、项目定位（企业视角，2026-08-03 确认）

企业要的不是技术新颖，而是：**稳定、能快速排查问题、有解决方案、流程流畅**。

- 创新是加分项，稳定与可排查性是及格线
- 企业 70% 的时间花在排查问题上，不是写新功能
- 一个能跑但出问题找不到原因的系统，比功能少但稳定的系统更危险

落到本项目的具体动作：
1. 稳定性：LLM 调用重试（指数退避）、工具层安全边界、控制台编码兜底
2. 可排查性：每张工单的结构化日志（处理轨迹、耗时、重试次数、失败原因）→ TODO 阶段5
3. 有方案：本开发日志、失败案例分析、技术选型文档
4. 流畅性：一次只做一个文件、每个文件能跑通再继续、评估驱动迭代

## 二、踩过的坑（按时间顺序）

### 坑 1：API Key 被填成打码占位符
- 现象：Claude Code 报 `API Error: Header '14' has invalid value: 'Bearer «redacted:sk-…»'`
- 原因：settings.json 里的 ANTHROPIC_AUTH_TOKEN 是 15 字符的占位符文本 `«redacted:sk-…»`（从聊天记录/工具输出复制的打码版本），不是真 key
- 排查方法：检查 key 长度（真 key 应 30+ 字符）、开头（sk-）、是否有非法字符
- 修复：从 DeepSeek 开放平台（platform.deepseek.com）复制真 key
- 教训：API key 只能从平台网页复制；聊天记录和工具输出里的 key 都是打码的假货

### 坑 2：模型名 deepseek-chat 已退役
- 现象：demo 运行报错/无法调用
- 原因：DeepSeek 于 2026-07-24 硬截止退役 `deepseek-chat`/`deepseek-reasoner`，必须用 `deepseek-v4-pro`/`deepseek-v4-flash`
- 教训：调用新框架/新 API 前先查最新文档，别用旧教程里的模型名；写代码前先确认依赖版本

### 坑 3：Windows 控制台 GBK 编码崩溃
- 现象：demo 打印中文+特殊符号（¥）时 `UnicodeEncodeError: 'gbk' codec can't encode character '\xa5'`
- 原因：Windows 控制台默认 GBK 编码，不支持部分 Unicode 字符
- 修复：脚本开头加 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`
- 教训：Windows 下跑 Python 脚本，控制台编码兜底是标配

### 坑 4：ccswitch 中转 vs 直连 DeepSeek
- 现象：demo 配置写死 base_url=https://api.deepseek.com，但环境里用的是 ccswitch 中转
- 决策：Python 项目直连 DeepSeek 官方 API，不依赖 ccswitch 桌面应用
- 理由：① 作品集代码要可移植，不能依赖本机装的中转工具；② 面试能讲"标准 OpenAI 兼容接入"；③ 中转站稳定性不可控
- 教训：区分"开发工具的环境"（Claude Code 走中转）和"项目代码的环境"（直连官方 API），两者互不干扰

### 坑 5：网络错误污染评估结果（最重要）
- 现象：第一次全量评估 56 条，售后类分类准确率只有 20%，以为是模型问题
- 真相：售后 15 条里 12 条是 `Connection error`（API 连接失败），评估脚本无重试，把网络错误全部记成失败，结果全被污染
- 修复：graph.invoke 包一层重试（指数退避 2/4/8 秒，最多 3 次，仅重试网络类错误）
- 教训：评估结果异常时，先检查"是不是评估基建的问题"，再怀疑模型。数据不可信时，调模型是浪费

### 坑 6：测试集标注错误（ground truth 不可信）
- 现象：TC-002/003 用户问"到哪了/发出来了没有"（物流问题），测试集却标注为订单类
- TC-013 退差价 2099 元超过 500 自动限额，系统正确转人工，测试集却期望 auto
- 修复：校准测试集标注，与业务规则对齐
- 教训：评估前先校准 ground truth。尺子不准，量什么都白搭

## 三、评估迭代过程（核心故事）

> **口径说明（2026-09-10 补）**：下表第 1–6 轮的数字基于 8-04 版测试集（56 条，期望转人工 17 条 = 30.4%）。2026-08-08 v2 重构（JSON→SQLite、工具虚实结合、评估体系统一）时测试集标注被重新校准，条数不变但期望转人工变为 34/59（57.6%），分类/行动指标随之变化。**最新口径以 README 和 eval/results.json 为准**：分类 100%、行动 96.6%、自动处理成功率 92.0%、失败 3 条。

| 轮次 | 分类准确率 | 行动准确率 | 自动处理成功率 | 转人工率 | 工具准确率 | 关键动作 |
|------|-----------|-----------|--------------|---------|-----------|---------|
| 第1轮 | 69.6% | 73.2% | 78.0% | 32.1% | 61.0% | 基线（无重试、标注有错） |
| 第2轮 | 96.4% | 82.1% | 100% | 10.7% | 70.0% | 加重试 + 校准标注 |
| 第3轮 | 98.2% | 87.5% | 90.0% | 30.4% | 97.5% | 加风险信号检测 + 先查后写 |

### 第 1 → 2 轮：修基建，不调模型
- 分类准确率 69.6% → 96.4%，售后 20% → 100%
- 核心不是模型变好了，而是：① 网络错误不再污染结果 ② 测试集标错了
- 教训：结果不可信时先修评估基建，别急着调 prompt

### 第 2 → 3 轮：评估逼出安全边界
- 发现 10 条"该转人工却被自动处理"的用例，这是客服事故级别的隐患：
  - 投诉威胁（12315/315/假货/赔偿）被自动回复
  - 物流异常（一周没更新）被自动处理
  - 已取消订单还扣款（财务纠纷）被自动处理
  - 快递丢失电话核实（诈骗风险）被自动回复
- 决策：decide_node 加确定性风险规则（不靠 LLM 判断）：
  - 消息含投诉/纠纷词 → 转人工
  - 物流状态异常 → 转人工
  - 已取消订单要求退款 → 转人工
- 效果：工具准确率 70% → 97.5%（先查后写规则），售后行动准确率 100%
- 副作用：物流规则过激，普通查询也被转人工（第 4 轮修复）

### 第 4 → 5 轮：数据、规则、标注三方没对齐（自己造的坑）
- 第 5 轮指令里"时间戳随机分布"导致：期望正常的运单被标旧（误判停滞），期望停滞的运单没标旧（规则漏检）
- 行动准确率 92.9% → 89.3%，教训：测试数据必须围绕测试用例精确设计，不能随机
- 情绪词删除和标注修改自相矛盾（改了标注又删了触发词）
- 修复：时间戳精确对齐用例、情绪词恢复、停滞规则按 updated_at 判断

### 第 5 → 6 轮：预期收敛
- 物流异常：只有"异常 + 情绪/投诉信号"才转人工，普通查询如实回复
- 加防诈骗信号：接到电话/短信 + 快递丢/核实信息 → 转人工
- 测试集校准 TC-020（退差价 100 元业务上允许，期望改为 auto）

### 第 6 轮结果（2026-08-03）：评估阶段完成 ✅
- 分类准确率 100% / 行动准确率 100% / 自动处理成功率 100% / 工具准确率 100%
- 转人工率 30.4% = 期望值 30.4%，完全吻合
- 失败 0 条。三类工单全部满分
- 关键：第 5 轮数据-规则-标注不对齐的坑修好后，规则和测试集精确对齐

### 第 7 轮（2026-08-04）：外部评审整改 + 留出集验证
外部评审发现 6 个问题，全部验证属实并修复：
1. **100% 过拟合风险** → 建留出集：56 条按 8:2 切（固定种子 42），train 44 条开发用，holdout 12 条只做最终验收
2. **history 是空壳** → main.py 接收 user_identifier，调用 get_user_history 查最近工单拼进 classify prompt（此前 API 传 []，面试话术与代码不符，最严重）
3. **运行时无重试** → eval 的 invoke_with_retry 逻辑封装进 nodes.py，3 处 LLM 调用全部启用（此前只在评估层有）
4. **先查后写是软约束** → handle_node 代码层强制：写操作前必须有对应查询成功，没有则自动先查，查询失败转人工
5. **工具覆盖率口径偏乐观** → README/日志注明：覆盖率只在 auto 用例统计，escalate 不计入分母
6. **classify 解析失败降级售后** → 改为转人工（category 空 + escalate_reason 说明）

**留出集验收结果（最关键）**：
- train 44 条：分类 95.5%（2 条分类争议但行动对）、行动 100%、工具 100%
- holdout 12 条：分类 100% / 行动 100% / 工具 100% / 自动成功率 100%

- 面试回答"100% 怎么来的"：先讲 6 轮迭代真实过程，再亮留出集数字，主动说明 100% 是测试集内
- **工具覆盖率口径**：只统计 auto 用例（escalate 用例不评判工具调用，tools_ok 为空不计分母）

## 五、架构决策记录（技术选型）

### 为什么 LangGraph 而不是其他框架
- LangChain：编排能力弱，全家桶但无亮点，面试默认过时
- LlamaIndex：偏 RAG，本项目以工具调用为主，用不上
- Dify：低代码平台，代码不可控，展示不了工程能力
- LangGraph：agent 编排事实标准，StateGraph 的节点/条件边/状态流转完美匹配
  工单处理流程，且个人此前学过编排引擎原理（拆任务/分派/并行/防死循环），
  理解成本低，能讲"我懂原理不只是会用 API"

### 为什么固定流程而不是 ReAct 循环
- 工单处理是确定性业务：分类 → 查证 → 决策 → 执行/转人工
- 固定流程可控、可评估、可讲；ReAct 循环在业务场景不可控
- 安全边界（金额限额、状态校验）写在工具层，LLM 无法绕过

### 为什么工具层做安全边界
- 已签收/已取消订单不可改地址、退差价 ≤500、退款 ≤1000 等规则写死在 tools.py
- 即使 LLM 决策错误，工具会拒绝执行——"LLM 可以犯错，但不能造成损失"
- 面试点：这是 LLM 应用的安全设计思想

## 六、方法论印证（来自知识库 ID 29《Agent 设计知识体系》）

> 项目做完后回看，我们的关键决策都能在学过的 Agent 设计方法论里找到依据。
> 面试话术：不是"我拍脑袋选的"，而是"我按方法论做的"。

| 方法论 | 本项目对应 |
|--------|-----------|
| 从 Workflow 开始，先确定性跑通再引入自主决策 | 固定流程（分类→查证→决策→执行/转人工），不用 ReAct 循环 |
| 先定义失败再定义成功 | 转人工设计：escalate 分支、工具层拒绝规则、风险信号检测 |
| 失效分析 > 架构优化 | 三轮评估迭代：不急着改架构，先修重试和测试集，再优化规则 |
| 工具分类决定安全策略（感知类可重试/执行类需审批） | query 类工具随便调，refund/update 类工具加金额和状态边界 |
| 状态驱动而非 Prompt 驱动 | LangGraph 的 StateGraph 显式管理工单状态流转 |
| 目标定义三要素（解决什么/输出什么样/何时算完成） | requirements.md 的痛点、指标、范围 |
| Guardrails 代码级硬上限 | 工具层限额（退差价 ≤500、退款 ≤1000）写死，LLM 无法绕过 |
| 很多 Agent 问题不是模型能力问题，而是目标/评估问题 | 第 2 轮教训：69.6%→96.4% 靠修评估基建，模型没动 |
| 模型 ≠ Agent，能力靠系统组装 | LangGraph 图 + 工具 + 状态 + 记忆，模型只是其中一个节点 |
| 五问题框架（目标/状态/能力/模型vs程序/终止条件） | 开发前先写 requirements.md 再动手，符合五问题顺序 |

面试可讲：知识库里学过 Agent 设计方法论 → 项目中实际踩坑验证 → 方法论和实战互相印证。

## 七、阶段 5-6：生产化（2026-08-04）

### 结构化日志
- 每张工单一条 JSON 日志，含 ticket_id、分类、工具调用、每步耗时（ms）、LLM 调用次数
- 日志即排查入口，出问题不用翻代码

### FastAPI 服务
- POST /api/ticket + GET / 简易 Web 页面
- user_identifier 关联历史工单，classify_node 用 history 做上下文

### 留出集
- 59 条按 8:2 切分（seed=42），47 train / 12 holdout
- 开发迭代只跑 train，holdout 留到最终验收

### 稳定性增强
- LLM 调用加到节点层重试（指数退避 2/4/8s，3 次）
