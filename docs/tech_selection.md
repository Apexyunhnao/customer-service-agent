# 技术选型文档

## 1. Agent 编排框架：LangGraph

**选型结论**：使用 LangGraph 的 StateGraph 作为 Agent 编排框架。

**依据**：
- 工单处理流程是确定性 DAG（分类 → 提取 → 执行 → 判断 → 回复），StateGraph 的节点/边/条件路由原生匹配
- TypedDict 定义共享状态，类型安全、可 IDE 补全，排查问题时状态变化一目了然
- 社区事实标准，文档成熟，DeepSeek 通过 langchain-openai 适配零成本

| 备选方案 | 为什么不选 |
|----------|-----------|
| LangChain AgentExecutor | 旧版 API，基于 ReAct 循环封装，对确定性流程过度抽象，调试困难 |
| LlamaIndex | 偏 RAG/文档检索场景，与工单处理的目标不匹配 |
| Dify/Coze 低代码 | 不可控——工具逻辑在黑盒内、调试依赖平台、私有化部署成本高 |
| 手写 if-else 流水线 | 初始可工作，但意图分类和信息提取无法做，LLM 调用无处安放 |
| CrewAI/AutoGen 多 Agent | 多 Agent 协作对单工单场景过度复杂，增加不确定性和 token 消耗 |

**关键取舍**：不用 ReAct 循环（思考-行动-观察循环），是因为工单处理是确定性业务。每一步做什么由规则和分类结果决定，不需要 Agent 自行探索。固定 DAG 的可评估性、可控性远高于开放式循环。

## 2. LLM 接入：DeepSeek via langchain-openai

**选型结论**：DeepSeek v4-pro，通过 OpenAI 兼容接口接入。

**依据**：
- 中文理解能力在客服场景中优于同价位模型
- OpenAI 兼容接口生态成熟，langchain-openai 一行配置即可切换
- 成本可控（每工单约 3 次 LLM 调用，token 消耗约 2-4K）

| 备选方案 | 为什么不选 |
|----------|-----------|
| GPT-4o | 成本高 3-5 倍，中文客服场景无明显优势 |
| 本地部署 Qwen/Llama | 需要 GPU 资源，运维成本高，不适合 MVP 阶段 |
| 直接调 HTTP API | 可以但没必要——langchain-openai 封装了重试、结构化输出等 |

## 3. 安全边界：工具层硬编码规则

**选型结论**：业务规则（金额限额、状态校验）写死在 Python 工具函数中，LLM 只负责选择调用哪个工具。

**依据**：
- LLM 可以犯错（幻觉、误解），但不能造成业务损失。退款 1000 元的限额不是 prompt 里的"建议"，是工具层的 `if amount > 1000: return success=False`
- 安全边界外显——审查代码即可确认规则，不需要逐条审计 LLM 输出
- 规则变更走代码 review 流程，不依赖 prompt 调优

| 备选方案 | 为什么不选 |
|----------|-----------|
| Prompt 约束 | 不可靠——LLM 可能被越狱、忽略、误解，无法保证执行 |
| RAG 知识库约束 | 同样不可靠，且增加系统复杂度 |
| 人工审批所有操作 | MVP 目标是自动化，全人工审批违背初衷 |

**已实现的安全规则**：
- `refund_price_diff`：金额 > 500 拒绝
- `process_refund`：金额 > 1000 拒绝，已取消订单拒绝
- `update_address`：已签收/已取消订单拒绝
- `process_exchange`：已取消订单拒绝
- `decide_node` 风险检测：敏感词、防诈骗、物流停滞、已取消+退款

## 4. 数据存储：SQLite

**选型结论**：SQLite 作为工单持久化存储。

**依据**：
- 单机演示场景，零部署、零配置、文件即数据库
- 读写并发在客服工单量级（日均 200 单）下完全够用
- Python 标准库 `sqlite3` 无额外依赖

| 备选方案 | 为什么不选 |
|----------|-----------|
| PostgreSQL/MySQL | 需要独立部署和维护，MVP 阶段过度 |
| Redis | KV 存储不适合工单的结构化查询需求 |
| 纯 JSON 文件 | 并发写不安全，查询需全量加载 |

---

## 5. Web 框架：FastAPI

**选型结论**：FastAPI + uvicorn。

**依据**：
- 异步原生支持，与 LangGraph 的同步调用不冲突
- Pydantic 模型与项目已有的 TypedDict 风格一致
- 自动生成 OpenAPI 文档，接口调试方便

| 备选方案 | 为什么不选 |
|----------|-----------|
| Flask | 同步框架，无类型校验，Pydantic 需额外集成 |
| Django | 重型框架，ORM/模板/中间件全量引入，过度 |
| Gradio/Streamlit | 面向 demo 的 UI 框架，不适合作为 API 服务 |
